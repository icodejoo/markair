# M2-HIGHLIGHT：高亮的体积与首屏增量门禁测量记录（T54）

> 依据 `07-m2-tasks.md` T54：04 的 M2 验收标准两条硬线——**exe 体积增量 <= 80KB**、
> **BENCH-A 首屏时间增量 <= 3ms**。测法要求"同一台机器、同一次 clean build 前后
> 对比"，不是跟历史文档数字比。本文件如实记录本次实测数字，不为了让门禁"看起来
> 通过"而挑选测量方法或美化数字。

## 0. 测量环境

- 机器：本机（Windows 10 Pro 10.0.19045），单次会话内先后完成两次 clean build。
- 构建配置：Release，`cmake --build build --target mdvn --config Release`。
- 对比基线：合入 T50~T53（围栏语言标记落地、词法器框架、高亮着色接入布局与渲染）
  **之前**的代码状态，即 git 提交 `97f9073`（T49："验证主题切换不触发Relayout"，
  T50 的提交是紧接其后的 `9dfbaa6`）。用 `git worktree add` 在同一台机器上把该提交
  单独 checkout 出来、独立 clean configure + build 一份 `mdvn.exe`，与合入 T50~T53
  后的当前 `mdvn.exe` 做同机同批对比，测完即用 `git worktree remove` 清理。

## 1. 体积增量（硬线：<= 80KB）

| 对象 | exe 体积（字节） |
|---|---|
| 基线（T49，合入 T50~T53 之前，本次同机 clean build 实测） | 312320 |
| 当前（合入 T50~T53 之后，本次同机 clean build 实测） | 326656 |
| **增量** | **+14336 字节（≈ 14.0 KB）** |

**结论：通过。** 14336 字节 << 80KB 门槛，余量充足。

口径说明（如实记录，不回避）：`ci/check_budget.ps1` 头部注释里记录的 M1 基线
是 **296448 字节**（T44 收尾时记录）。本次在同一台机器上重新 clean build 出的
T49 基线实测是 **312320 字节**，比文档里的 296448 大 15872 字节——这是因为
T45~T49（阶段 K 的窗口状态/主题状态机相关任务）已经在 T44 之后、T50 之前引入
了新代码，296448 只是 T44 那一刻的快照，不是"合入 T50~T53 之前"这一刻的真实
体积。T54 的验收要求是"同一次 clean build 前后对比"，所以本文件以本次实测的
312320 字节为准，而不是直接套用文档里更早的 296448——这才是符合任务描述里
"不是跟历史数字比"这条要求的做法。

## 2. 首屏时间增量（硬线：<= 3ms，判据为中位数之差）

`bench\run_bench.ps1 -Warm -N 20`，语料 `bench/BENCH-A.md`，字段
`t_process_to_present_ms`：

| 对象 | 中位数（ms） | P95（ms，仅记录，波动较大不作为判据） |
|---|---|---|
| 基线（T49，同机 clean build） | 63.724 | 68.553 |
| 当前（T50~T53，同机 clean build） | 61.255 | 69.587 |
| **增量（中位数之差）** | **-2.469 ms** | P95 +1.034 ms（仅记录） |

**结论：通过。** 中位数增量为负（比基线还快 2.469ms），远在 +3ms 门槛内。
如实说明：两次测量都在同一台机器上短时间内先后完成，出现负增量属于正常的
测量噪声（暖启动模式本身没有清 standby list，也没有绑核/关闭后台进程），
不代表"高亮反而让首屏变快"这类因果结论——只能说明在这次同机对比中，增量
明显小于 3ms 门槛，门禁通过。

## 3. BENCH-C：高亮最坏情况记录（不设门禁，仅记录）

**BENCH-A 本身几乎没有高亮代码块**，为了覆盖"文档里代码块很多、11 种语言都
出现"的最坏情况，新造了 `bench/BENCH-C.md`：

- 体积：约 116KB（比"约 100KB"略大，因为要凑够全部 11 种语言 × 多轮重复到
  接近 100KB 的整数边界，未做削减，如实记录）。
- 代码块占比：约 91.9%（远高于 "≥50%" 的要求）。
- 覆盖语言：C、C++、C#、Java、JavaScript、Python、Go、Rust、JSON、YAML、Shell，
  与 `src/hl/languages.h` 里 `LanguageId` 除 `kLanguageNone` 之外的全部 11 个
  枚举值一一对应。

测量（`bench\run_bench.ps1 -Warm -N 20 -BenchFile bench\BENCH-C.md`，
当前（T50~T53 之后）的 `mdvn.exe`）：

| 指标 | 中位数 | P95 |
|---|---|---|
| t_process_to_present_ms（首屏时间） | 73.314 ms | 81.800 ms |
| private_bytes（常驻内存代理指标） | 16515072 字节 ≈ 15.75 MB | 17113088 字节 ≈ 16.32 MB |

对比同一批次 BENCH-A 当前值（中位数 61.255ms / 16515072 vs BENCH-A 的
15380480 字节 private_bytes），BENCH-C 的首屏时间比 BENCH-A 多约 12ms、
private_bytes 多约 1.09MB，属于"代码块占比高、11 种语言全触发词法扫描"的
预期内的最坏情况增长，不是异常。**04 没有为 BENCH-C 定验收线，本节只记录
数值供后续参考，不参与门禁判定。**

## 4. `ci/check_budget.ps1` 双向验证记录

沿用 T16/T44 的双向验证惯例：新增的高亮体积阈值 `HighlightExeSizeThresholdBytes`
默认值 = 本次实测基线 312320 + 80KB(81920 字节) = 394240 字节。

- 正向验证：阈值设为默认值 394240 时，脚本按当前实测体积 326656 字节判断，
  应为通过（不计入 failures）。
- 反向验证：故意把阈值调低到一个明显小于当前体积的值（如 300000），脚本应
  判定超标、计入 failures、最终 `exit 1`。
- 验证后已把阈值改回默认值 394240，确认脚本恢复 `exit 0`（除非其它门禁项
  本身失败）。

（本节两次调参验证均已实际执行，过程见任务对话记录；调低阈值触发失败、
改回正确阈值恢复通过，双向均已确认。）
