## 6. T67：11 种语言陷阱语料人工过一遍记录

语料位置：`bench/hl/sample.{c,cpp,cs,java,ts,py,go,rs,json,yaml,sh}` 共 11 份 +
`bench/hl/ALL.md`（拼合版，围栏标记逐一对照 `src/hl/languages.cpp` 的
`kAliases` 表选取：`c`/`cpp`/`cs`/`java`/`ts`/`py`/`go`/`rs`/`json`/`yaml`/`sh`，
全部能命中对应 `LanguageId`，不会落到 `kLanguageNone`）。

判断方法：没有跑 GUI 渲染，而是逐字节对照 `src/hl/lexer.cpp`（T51 的手写状态
机）实际实现推演每份样例会产生什么 token，而不是凭直觉猜测——这样能发现
实现里"看似支持但其实没接上"的分支缺口。

### 6.1 C（sample.c）—— 可接受，0 处必修

`R` 开头的原始字符串在 C 里不存在，样例只测了未闭合块注释：故意放在文件
末尾单独一节，`TryBlockComment` 找不到 `*/` 时扫到文本末尾即停止，不会
反向影响前面已经扫描过的正文。中文字符串/注释按非 ASCII 字节直接归入
标识符/普通内容，不参与状态机跳转，表现正确。

### 6.2 C++（sample.cpp）—— 可接受，0 处必修

`R"(\d+\.\d+)"` 命中 `TryRawString` 里专门写的 `kLanguageCpp` 分支（只支持
`R"(...)"` 这一种最简单定界符形式，样例正好用的是这种），正确识别为一个
字符串 token。末尾的未闭合块注释与 C 情况相同，表现正确。

### 6.3 C#（sample.cs）—— 可接受（2 处观察，未触发必修）

`$"..."` 与 `@"..."`：`LanguageRule` 里 `kLanguageCSharp.supportsRawStrings=true`，
但 `TryRawString` 函数体里**没有 `kLanguageCSharp` 的分支**（只有
Cpp/Python/Go/Shell 四个分支）。实际退化路径是：`$`/`@` 各自被 `ScanPunct`
当成一个独立标点 token，随后紧跟的 `"..."` 交给通用 `TryQuotedString` 按
双引号扫描。因为样例里插值字符串和逐字字符串内部都没有出现"提前闭合"的
裸引号，通用扫描恰好能扫到正确的结束引号，**字符串边界本身是对的**，只是
`$`/`@` 前缀和 `{name}` 插值表达式不会被特殊染色（会被当成字符串内容的
一部分，连同大括号一起上字符串色）。这是"少染色"而不是"染错颜色导致误
读"，判定可接受。

需要记录的潜在风险（样例未触发，不计入本次必修，但如实提醒）：真实 C#
逐字字符串里若出现 `""` 表示内嵌一个字面双引号（如 `@"a""b"`），当前的
通用 `TryQuotedString` 会在第一个 `"` 处就把字符串判定为闭合，导致后半段
错位。这是 `TryRawString` 缺少 C# 分支的直接后果，建议后续任务（不在
T67 范围内）补上专门分支。

### 6.4 Java（sample.java）—— **必修：1 处**

`"""文本块"""`：`LanguageRule` 同样标了 `supportsRawStrings=true`，但
`TryRawString` **没有 `kLanguageJava` 分支**。实际扫描顺序是：开头三个
`"` 里，第 1、2 个 `"` 被 `TryQuotedString` 当成"空字符串"闭合（quote 对
quote 之间 0 个字符），第 3 个 `"` 重新开一个字符串，继续扫描直到文本块内容
里第一处裸双引号（`不需要转义` 前后的 `"`）被误判为闭合定界符——之后的
内容（`不需要转义`、后续中文说明、结尾的 `"""`）被拆成若干段错位的
字符串/标点 token，颜色在文本块内部会来回跳变。这段错位在文本块结束后
会被"用完"所有裸引号后自然收尾（不会一直吞到文件末尾），但**块内部这几行
的误标记数远超"每份不超过 2 处"的验收线**，判定为必修：需要在
`TryRawString` 里补一个 `kLanguageJava` 分支，识别 `"""` 三重引号并整体
消费到下一个 `"""` 为止（逻辑上可以直接复用 Python 三引号分支的写法）。

### 6.5 TS（sample.ts）—— 可接受（1 处观察）

正则字面量 `/a\/b/`：规则表里没有为任何语言建模"正则字面量"这个 token
类别，`lexer.cpp` 也确实没有处理。实际表现是 `/`、`a`、`\`、`/`、`b`、`/`
被拆成一串标点/标识符 token，不会被误判成字符串，也不会吞掉后面的
`divide` 函数——只是没有整体正则高亮，可接受。模板字符串 `` `...${...}` ``
命中 JS/TS 共用的 `stringDelimiters "\"'`"`，反引号被 `TryQuotedString`
当普通引号扫描，样例里没有嵌套反引号，闭合正确。

### 6.6 Python（sample.py）—— 可接受，0 处必修

三引号 `'''...'''`/`"""..."""` 命中 `TryRawString` 里专门的
`kLanguagePython` 分支，内容原样消费到配对的三引号为止，表现正确。
f-string 前缀 `f"..."`：`f` 先被 `ScanIdentifier` 当成一个独立标识符
（不在关键字表/内置表里，归为 `kTokenOther`），紧跟的字符串再单独扫描——
是"少一层归并"而不是"染错"，可接受。

### 6.7 Go（sample.go）—— 可接受，0 处必修

反引号原始字符串命中 `TryRawString` 的 `kLanguageGo` 分支，内容原样消费
到下一个反引号为止；样例里反引号字符串内嵌了单引号 `'张三'`，因为闭合
条件只认反引号、不认单引号，不会提前截断，表现正确。

### 6.8 Rust（sample.rs）—— **必修：2 处，是本次过一遍里最严重的发现**

1. **生命周期标注 `'a` 被误判为字符字面量起点，吞掉一大段代码。**
   `LanguageRule.kLanguageRust.stringDelimiters` 里含单引号 `'`，但
   `TryRawString` 里**没有为 Rust 写生命周期专用分支**（T51 那条注释自己
   也写了"'a 生命周期标注需要 T51 扫描器单独处理"，但对照 `lexer.cpp`
   实际代码，这个分支没有落地）。实际路径是：遇到 `<'a>` 里的 `'`，
   `TryQuotedString` 把它当成字符字面量的开引号，quote 记为 `'`，然后一路
   往后扫描，直到样例里**下一次出现单引号**——也就是文件最后一行的字符
   字面量 `'x'` 的开引号。这意味着从 `struct Greeter<'a> {` 中的那个 `'`
   开始，一直到 `let ch: char = '` 之前的**几乎整个文件正文**（包括
   `impl<'a>`、`fn new`、`format!` 调用、`println!` 语句、真实字符串
   `"你好，{}!欢迎使用 mdvn"` 等）都会被当成同一个"未终止字符字面量"的
   内容一次性染成字符串颜色，直到 `'x'` 的 `'` 把它闭合。这正是任务描述
   里点名的"Rust 高亮最经典的坑"，本次人工过一遍确认**当前实现确实会
   踩上**，误标记范围远超"每份不超过 2 处"的线，判定必修。
2. **`r#"..."#` 原始字符串未实现，被拆解成错位片段。**
   同 C#/Java 的情况一样，`kLanguageRust.supportsRawStrings=true` 但
   `TryRawString` 没有 `kLanguageRust` 分支。`r#"路径示例: "C:\Users\测试""#`
   实际会被拆成：标识符 `r`、标点 `#`、字符串 `"路径示例: "`（在第一个内嵌
   裸引号处就提前闭合）、随后 `C:\Users\测试` 变成散落的标识符/标点、
   再遇到 `""` 里第一个 `"` 开一个空字符串、第二个 `"` 又开一个新字符串
   一路吞到 `#` 后面——整段原始字符串的染色是错的。判定必修，建议补
   `kLanguageRust` 分支识别 `r#"..."#`（可以先只支持单个 `#` 的最简形式，
   与 Cpp 分支的取舍一致）。

   两处必修的修复方式类似：都需要在 `TryRawString` 里补对应语言的专用
   分支，并且 Rust 的生命周期分支必须写在"尝试当成字符字面量解析"之前
   ——用"`'` 后面是标识符起始字符且再往后不是紧跟单引号"这类启发式
   区分 `'a`（生命周期）与 `'x'`（字符字面量），否则两个语法在词法层面
   确实容易互相绞在一起。

### 6.9 JSON（sample.json）—— 可接受，0 处必修

`\u4f60` 这类 Unicode 转义：`TryQuotedString` 的通用转义逻辑只是"遇到
`\` 就跳过它和后面 1 个字节"，对 `\u4f60` 来说会把 `\u` 当一对跳过，剩下
`4f60` 当普通字符继续扫描，不会提前触发闭合引号，整段字符串仍然被正确
识别为一个 token，只是不理解 `\u` 后面还跟 4 位十六进制这个结构——不影响
染色正确性，可接受。

### 6.10 YAML（sample.yaml）—— 可接受，0 处必修

锚点 `&默认值`、别名 `*默认值`、块标量指示符 `|`/`>`：`kLanguageYaml` 是
`kStructured` 风格且规则表没建模这几类符号，`&`/`*`/`|`/`>` 都会退化成
`ScanPunct` 产生的普通标点 token，不会被专门染色，但也不会造成任何跨行的
错误吞并——块标量内容（包括里面的双引号字符串 `"你好，世界"`）按普通
YAML 内容逐行扫描，表现是"没有特殊语义染色"而不是"染错"，可接受。

### 6.11 Shell（sample.sh）—— 可接受（1 处已知限制，样例未触发）

`$(...)` 命令替换：`$` 不在任何定界符集合里，退化成独立标点 token，`(`/`)`
也是独立标点，不会被识别成"命令替换"整体，但不影响其余部分，可接受。
heredoc `<<EOF ... EOF`：词法器完全不认识 heredoc 语法，`<<EOF` 被拆成
标点+标点+标识符 `EOF`，heredoc 主体的每一行会被当成**真正的 Shell 代码**
继续扫描——本样例里主体内的双引号/单引号都是成对出现，通用引号扫描能
正确闭合，没有跨出 heredoc 边界造成误吞。但这是一个已知限制，如实记录：
如果 heredoc 主体内出现不成对的引号或以 `#` 开头的一行，当前实现会把
后续内容误判为字符串/注释并可能吞到远超预期的范围，只是本次样例没有
构造这种最坏情况，不计入本次必修统计。

## 7. 后续任务：3 处必修项修复与复核（`src/hl/lexer.cpp::TryRawString`）

在 `TryRawString` 里补了三处专用分支（全部写在通用 C++/Python/Go/Shell
分支之前，Rust 的两个分支还写在了函数最前面，保证优先于 `TryQuotedString`
生效）：

1. **Rust 生命周期 `'a` vs 字符字面量**：遇到 `'` 时先看后一个字节——
   若是 `\` 且转义序列后紧跟闭合 `'`，判定为转义字符字面量（`'\n'`、
   `'\''` 等）；否则若是标识符起始字符，继续扫描标识符长度，若正好 1 个
   字符且紧跟闭合 `'`，判定为普通字符字面量 `'x'`；其余情况（标识符长度
   ≥2，或紧跟的不是闭合 `'`）判定为生命周期标注，token 只覆盖 `'` + 标识
   符本身，不吞闭合引号（因为本来就没有）。
2. **Rust `r#"..."#`**：命中 `r#"` 后扫描到下一次出现 `"#` 为止（只支持
   单个 `#`，与 C++ 的 `R"(...)"` 分支取舍一致），找不到就扫到文本末尾。
3. **Java `"""文本块"""`**：命中 `"""` 后扫描到下一次出现 `"""` 为止，
   逻辑与 Python 三引号分支一致，找不到就扫到文本末尾。
